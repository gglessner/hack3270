# hack3270: Guardrailed Mainframe Application Pen Testing

Designed for authorized penetration testing of scoped CICS/KICKS applications. Constrains scope, limits aggression, and requires human approval before escalation. All actions and payloads are automatically logged to SQLite3 by the MCP proxy for full traceability. For unrestricted mainframe pen testing knowledge (lab/CTF use), see the companion `tn3270-pentest` skill.

## Scope Definition

### Transaction Prefix Locking

When you first encounter the entry-point transaction, extract its **2-character prefix** and lock all testing to that prefix for the entire session.

**Example:** Entry point is `MCGM` -- prefix is `MC`.

- **In scope:** `MCGM`, `MCMM`, `MCAD`, `MCOR`, `MCLG`, `MCXX` -- any `MC**` transaction
- **Out of scope:** `CESN`, `CEMT`, `CEDA`, `CECI`, `CEDF`, `CEBR`, `CSSF`, or any other prefix

**Rules:**
- You may **discover** out-of-scope transactions (via hidden fields, menus, etc.) -- document them but do NOT invoke them
- CLEAR + transaction code is allowed only for in-scope prefix codes
- Navigate the application using its own menus and PF keys, not arbitrary transaction codes
- If the human needs testing outside the prefix, they must explicitly authorize it

### What Is In Scope

- All screens reachable via in-scope transactions
- All input fields, protected fields, and hidden fields on those screens
- AID key behavior on those screens
- In-application authentication (supervisor codes, PINs, app-level passwords)
- Protected field tampering on in-scope screens (prices, quantities, status codes)
- TSO escape testing via in-scope protected field tampering (prove it, validate with `TIME`, return immediately)

### What Is Out of Scope

- System transactions (CES\*, CEM\*, CED\*, CEC\*, CEB\*, CSG\*)
- VTAM APPLID enumeration
- TSO post-exploitation (LISTCAT, EDIT, SUBMIT, dataset browsing)
- JCL submission or SPOOLOPEN
- RACF/ACF2/TopSecret authentication brute force
- Full transaction code enumeration (scanning all 4-character combinations)
- Any transaction outside the 2-character prefix

## Hard Guardrails

These rules are absolute. Never violate them regardless of what is discovered during testing.

### 1. No System Transaction Execution

Never execute IBM-supplied CICS system transactions: CESN, CESF, CEMT, CEDA, CEDB, CECI, CEDF, CEBR, CSGM, CSSF, or any CES\*/CEM\*/CED\*/CEC\*/CEB\*/CSG\* variant. These modify CICS region configuration and are outside the target application. If you discover that one is accessible, document the finding and report it -- do not use it.

### 2. TSO Escape: Test but Do Not Exploit

If a protected field on an in-scope screen allows TSO escape (replacing the transaction routing code causes a `READY` prompt), this is a valid finding. To confirm:

1. Send a replacement value to the protected routing field (e.g., `send_field_data(text="ABCD", field_address=1)`)
2. If `READY` appears, run `TIME` to validate live TSO access
3. Document the finding (screen, field address, payload, TIME output)
4. **Immediately** return to the application via CLEAR + entry-point transaction or LOGOFF

If `TIME` does not return expected output (e.g., customized TSO environment suppresses it), do NOT attempt alternative commands like `STATUS`, `HELP`, or `PROFILE`. Document the finding as "suspected but unconfirmed TSO routing escape" and return immediately.

Do NOT run any other TSO commands. No LISTCAT, no EDIT, no SUBMIT, no LISTDS, no PROFILE. The `READY` prompt (plus `TIME` output if available) is sufficient proof.

### 3. No JCL Submission or SPOOLOPEN

Never submit batch jobs. Never use SPOOLOPEN, SPOOLWRITE, or write to transient data queues (CXRA) for execution. This is system-level access, not application testing.

### 4. No System Authentication Brute Force

Never brute force RACF/ACF2/TopSecret authentication (CESN sign-on, TSO logon). These security managers enforce lockout thresholds (typically 3-5 failures) and locking an account affects real users on the system.

**In-application authentication is different.** Supervisor codes, in-app PINs, and application-level passwords handled by the COBOL program are part of the application under test. These typically have no system lockout mechanism and are fair game for brute force with reasonable rate limiting.

### 5. No Overflow Fuzzing Without Approval

Do not send overflow payloads (long strings exceeding field length) unless the human explicitly approves. Overflow payloads can trigger SOC4/ASRA abends that crash shared CICS regions and affect other users. Stick to `decimal` and `sql` payload categories by default.

**If the human approves overflow testing**, use a graduated approach:
1. Start with 1.2x field length using safe repeating characters (e.g., `AAAAAA`)
2. If stable, increase to 1.5x field length
3. Only then try special characters if needed
4. Cap at 5 overflow attempts per field unless re-approved
5. After each payload, run `get_screen()` and verify the region is still responsive before the next attempt

### 6. Stop on Abend -- Never Repeat

If any action causes an abend (ASRA, SOC7, SOC4, AICA, AKCS, or any other), immediately:

1. Document the exact action/payload that caused it
2. Stop that line of testing
3. Report the finding to the human
4. **Never repeat the payload** that caused the abend

An abend in a shared CICS region affects all users. Even in a dedicated test region, repeated abends waste resources and may trigger operator alerts.

### 7. No Wide Transaction Enumeration

Do not run `fuzz_transaction_codes()` against full wordlists like `cics-default-transactions.txt`. Only enumerate transactions within the in-scope 2-character prefix. For a prefix like `MC`, you may test `MC` + 2 alphanumeric characters (up to ~1,296 combinations), but do so with delays (0.5s minimum) and stop if you see errors or lockout indicators.

### 8. Sensitive Data Handling

During testing, do not capture or reproduce verbatim any fields that appear to contain PII, payment card data, account numbers, or other regulated content (based on format, labels, or context). In reports and communications with the human, always mask such values (e.g., replace `1234-5678-9012-3456` with `[REDACTED-ACCT-3456]` or `XXXX-XXXX-XXXX-3456`; replace `$1,234.56` with `[REDACTED-AMT]`). If a finding involves sensitive data modification, describe the impact generically (e.g., "tampering with account balance field accepted without validation") unless the human directs otherwise.

## Escalation Protocol

The following actions require explicit human approval before proceeding. Ask the human and wait for confirmation.

- **Out-of-prefix testing** -- invoking any transaction outside the 2-character prefix
- **Overflow fuzzing** -- sending payloads that exceed field length
- **Data modification** -- changing values in the application (vs. read-only analysis)
- **System transaction access** -- executing CES\*/CEM\*/CED\* transactions even if discovered as accessible
- **Post-abend testing** -- resuming any testing after causing an abend
- **System auth brute force** -- brute forcing CESN, TSO, or RACF-protected resources

When escalating, explain to the human:
1. What you want to do
2. Why (what you expect to discover)
3. What the risk is (e.g., Low: minor disruption; Medium: potential abend or slowdown; High: possible account lockout, data corruption, or region impact)

If the human denies approval, accept it and move on. Do not revisit the same escalation request unless new evidence emerges that changes the risk assessment.

## Rate Limiting

| Operation | Limit | Delay |
|-----------|-------|-------|
| In-app brute force (PINs, supervisor codes) | No hard cap; report progress at intervals of no more than 20 attempts (e.g., every 20, or on milestones like 50/100) | 1.0s between attempts |
| System auth (CESN, TSO) | **FORBIDDEN** unless human approves | N/A |
| Input field fuzzing | `decimal` + `sql` categories only (no `overflow`, no `control`) | 0.5s between payloads |
| In-scope transaction enumeration | Prefix + 2 chars max (~1,296 codes) | 0.5s between attempts |
| AID key scanning | All keys, one screen at a time | 0.5s between keys |
| General screen interactions | No specific limit | 0.3s minimum between actions |

## Safe Pen Test Methodology

Follow these steps in order. The approach is **observation-first, interaction-second**.

### Phase 1: Reconnaissance (Read-Only)

**Step 1. Connect and identify the entry point.**
- Use `connect_api()` or `ping()` to verify connectivity
- Identify the entry-point transaction on screen (e.g., `MCGM`)
- Extract the 2-character prefix (e.g., `MC`) -- this is your scope for the entire session
- State the prefix to the human: "Scope locked to prefix XX"

**Step 2. Establish a baseline.**
- Perform 3-5 normal, valid interactions (menu navigation, ENTER) to baseline response times and screen behavior
- This helps detect anomalies later (e.g., slowdowns indicating potential runaway tasks or region stress)

**Step 3. Map the application.**
- Navigate through every menu option using PF keys and menu selections
- Record every screen: transaction code, title, purpose, navigation path
- Build a complete screen map before any active testing
- Note which screens have input fields, protected fields, or hidden elements

**Step 4. Analyze every screen.**
On each screen, run these in order:
1. `get_screen()` -- capture the visual layout
2. `analyze_screen_fields()` -- discover all fields (input, protected, hidden)
3. `get_hidden_fields()` or `analyze_hidden()` -- find non-display fields
4. `get_input_fields()` -- identify editable fields
5. Note protected fields containing financial data, status codes, or transaction routing codes

### Phase 2: Active Testing (Conservative)

**Step 5. Test AID keys on each screen.**
- Test PA1, PA2, PA3 manually on every major screen -- these often trigger hidden navigation
- Use `scan_aid_keys()` for PF key scanning, but be aware it may exit the app via PF3
- Test PF3 last on each screen (it typically exits)
- If a key navigates to a new screen, analyze that screen fully, then return
- If a hidden AID key leads to a new screen, test AID keys on THAT screen too (nested hidden functions)

**Step 6. Test hidden field options.**
- If hidden fields reveal menu options or values, enter them into the appropriate input fields
- Document what each hidden option does

**Step 7. Test direct transaction access.**
- Use CLEAR + in-scope transaction codes to test which can be accessed directly (bypassing menu navigation)
- Only test codes within the 2-character prefix
- Document any transactions accessible directly that aren't shown in menus

**Step 8. Test input validation.**
- On input fields, test with `fuzz_field()` using `decimal` and `sql` payload categories only
- Do NOT use `overflow` or `control` categories without human approval
- Watch for abends after each payload -- if one occurs, stop immediately (Guardrail 6)
- Document any fields that accept invalid input without error

**Step 9. Test protected field tampering.**
- Analyze protected fields for business-critical data (prices, quantities, status codes, account numbers)
- Report findings to the human before modifying values
- If approved, use `send_field_data()` or `send_raw_hex()` to modify protected field values
- Test whether the server validates the modified values or blindly accepts them

**Step 10. Test TSO escape.**
- Check if any protected field contains the current transaction routing code (typically at buffer address 1)
- If found, attempt to replace it with a non-application value (e.g., `ABCD`)
- If `READY` prompt appears: run `TIME` to confirm live TSO access
- Document the finding (screen, field address, payload, TIME output)
- Immediately return to the application -- do NOT run further TSO commands
- If no `READY` prompt, the application validates routing codes server-side -- document this as a positive security control

### Phase 3: Reporting

**Step 11. Document and report.**
- Compile all findings into a structured report
- Include severity ratings (Critical, High, Medium, Low, Informational)
- For each finding: description, proof of concept, impact, remediation
- Include positive findings (security controls that worked correctly)

## Recovery Procedures

### Accidentally Exited the Application
Immediately re-enter via CLEAR + entry-point transaction. Do not explore whatever screen you landed on.

### Landed on Unknown/Out-of-Scope Screen
Press PF3 or CLEAR to return. Do not interact with the screen. If PF3 doesn't work, try CLEAR + entry-point transaction.

### Caused an Abend
1. Stop immediately
2. Record the abend code (ASRA, SOC7, SOC4, AICA, etc.)
3. Record the exact payload/action that caused it
4. Report to the human
5. Do NOT retry the payload
6. Wait for the CICS region to recover (the abend screen usually clears with CLEAR)
7. Resume testing other areas only after confirming the region is responsive

### Account Locked Out
Stop all testing immediately. Report to the human. Do not attempt to unlock the account or try other credentials.

### Reached TSO Prompt (Intentional Test)
1. Run `TIME` to validate live access
2. Document the finding
3. Do NOT run any other commands
4. Return via CLEAR + entry-point transaction, or type `LOGOFF`
5. Report the finding

### Reached TSO Prompt (Accidental)
Do NOT execute any commands. Immediately return via CLEAR + entry-point transaction, or type `LOGOFF`.

### Accidentally Landed on a System Transaction Screen
If navigation unexpectedly reaches a system transaction screen (CEMT, CECI, CESN, etc.), do NOT interact with it. Immediately issue CLEAR + entry-point transaction. Document the navigation path that led there -- the fact that a system transaction is reachable from within the application is itself a finding (insecure menu routing or unprotected transaction access).

### Application Rejects Inputs After Tampering
If the application suddenly rejects all inputs, resets field values, or logs you out after protected field tampering attempts, this likely indicates TN3270 field integrity checking or application-level tampering detection. Document this as a **positive security control** (the application or TN3270 layer detected and blocked manipulation attempts). Pause that testing vector and move on unless the human re-authorizes.

### Application Becomes Unresponsive
1. Wait 10 seconds
2. Try pressing ENTER or CLEAR
3. If still unresponsive, report to the human
4. Do NOT send rapid repeated keystrokes (this worsens the condition)

## Technical Reference

### Unformatted vs Formatted Screens

**Unformatted** (after CLEAR, or blank screen with no fields):

```
AID + cursor_addr(2 bytes) + EBCDIC_data + IAC_EOR
```

Do NOT include SBA (0x11) on unformatted screens. There are no fields, so SBA corrupts the transaction name and causes APCT abends.

**Formatted** (has input/protected fields):

```
AID + cursor_addr + [SBA + field_addr + data]... + IAC_EOR
```

Use `analyze_screen_fields()` to discover field addresses first.

### Key 3270 Orders

| Byte | Order | Purpose |
|------|-------|---------|
| 0x11 | SBA | Set Buffer Address |
| 0x1D | SF | Start Field (attributes) |
| 0x29 | SFE | Start Field Extended (hidden fields use this) |
| 0x3C | RA | Repeat to Address |
| 0x13 | IC | Insert Cursor |

Screen: 24x80 = 1920 positions. Position = row\*80 + col (0-indexed).

### AID Keys

| Hex | Key | Hex | Key |
|-----|-----|-----|-----|
| 0x7D | ENTER | 0x6D | CLEAR |
| 0xF1-0xFC | PF1-12 | 0xC1-0xCC | PF13-24 |
| 0x6C | PA1 | 0x6E | PA2 |
| 0x6B | PA3 | 0xF0 | SYSREQ |

PA keys transmit only the AID byte (no field data). Developers sometimes use them as hidden shortcuts to admin screens, debug modes, or easter eggs. Always test PA1-PA3 on every screen.

### Abend Codes

| Code | Meaning | Action |
|------|---------|--------|
| APCT | Program not found/disabled | Low severity -- likely a typo or missing program. Retry with correct transaction. |
| ASRA | Program check (crash) | **STOP.** Critical finding. Document payload. Do not repeat. |
| AICA | Runaway task | **STOP.** Critical finding. May indicate infinite loop. |
| AEY7 | Timeout | Medium. The operation took too long. Wait and retry once. |
| SOC7/S0C7 | Data exception (bad decimal) | **STOP.** Critical finding. Input validation failure. |
| SOC4/S0C4 | Protection exception (memory) | **STOP.** Critical finding. Possible buffer overflow. |
| ASRB | Operating system abend | **STOP.** Critical. Report immediately. |
| AEIP | Invalid EXEC CICS command | Low severity. Informational. |
| AKCS | Storage violation | **STOP.** Critical finding. |
| AEY9 | Not authorized (security violation) | Informational/Low. Note if unexpected during in-scope testing -- may indicate an ESM check on the resource. |

### Hidden Fields

CICS applications hide fields using SFE (Start Field Extended) with a non-display attribute. Always run `analyze_hidden()` or `get_hidden_fields()` on every screen.

Common findings:
- Hidden menu options with real functionality
- Status flags controlling business logic (e.g., "Purchaseable: Y/N")
- Internal IDs, debug data, authorization tokens

Hiding is NOT access control. If the server doesn't validate separately, hidden values can be submitted by anyone.

### Protected Field Tampering

The terminal prevents typing in protected fields, but `send_field_data()` and `send_raw_hex()` bypass this entirely. COBOL's `RECEIVE MAP` reads ALL fields from the input stream, including protected ones.

Use `analyze_screen_fields()` to find protected fields, then `send_field_data(text="value", field_address=addr)` to modify them.

### TSO Escape Indicators

A protected field near buffer address 0-5 that contains the current 4-character transaction code (matching what's visible in the screen header) is a routing field. If this value changes as you navigate between screens (e.g., `MCMM` on main menu, `MCAD` on address screen), the application relies on the client-side value for transaction routing -- a critical vulnerability.

To test: replace the value with any unrecognized code (e.g., `ABCD`). If `READY` appears, TSO escape is confirmed.

## Tool Quick Reference

**Connection**: `connect_api`, `reconnect_api`, `ping`, `check_connection`
**Screen**: `get_screen`, `get_screen_raw`, `get_screen_raw_hex`, `find_text`, `get_text_at`
**Fields**: `analyze_screen_fields`, `get_input_fields`, `get_hidden_fields`, `analyze_hidden`
**Send**: `send_enter`, `send_clear`, `send_aid_key`, `send_pf_key`, `send_command`, `send_field_data`, `send_fields_data`, `send_raw_hex`, `build_and_send_packet`
**Attack**: `fuzz_field`, `fuzz_all_input_fields`, `brute_force_field`, `scan_aid_keys`, `setup_injection`, `inject_value`
**Session DB**: `load_database`, `list_databases`, `get_logs`, `get_log_entry`, `replay_client_data`, `replay_sequence`
**Utility**: `convert_ascii_to_ebcdic`, `convert_ebcdic_to_ascii`, `encode_buffer_address`, `decode_buffer_address`, `check_abend`, `wait_for_text`, `wait_for_screen_change`

**Tool-specific guardrails:**
- `fuzz_field` / `fuzz_all_input_fields` -- restricted to `decimal` and `sql` categories; `overflow` and `control` require human approval + graduated sizing (Guardrail 5)
- `brute_force_field` -- allowed only for in-app auth (PINs, supervisor codes); report progress every 20 attempts; never use against CESN/TSO (Guardrail 4)
- `fuzz_transaction_codes` -- never use with default/full wordlists; only with a custom prefix-limited list matching the 2-char scope, with 0.5s+ delays (Guardrail 7)
- `send_raw_hex` -- use with caution; always run `analyze_screen_fields()` first to understand field layout before constructing raw packets
- `send_field_data` -- preferred over `send_raw_hex` for protected field tampering (handles SBA/EBCDIC automatically); supports `aid` parameter for submitting with non-ENTER keys
- `send_fields_data` -- use for multi-field forms (login, search); fills all fields before submitting once
